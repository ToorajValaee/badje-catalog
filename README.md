# بادجه — HTML Catalog Engine

This is the deployable version that converts uploaded PDF catalogs into normal web pages **without converting PDF text to HTML**.

Each PDF page is rendered as a high-resolution WebP image. PDF link rectangles are extracted and placed above the page image as transparent HTML links. Internal PDF links switch to the matching catalog screen without document scrolling; external URLs remain external links.

## Runtime architecture

- Next.js 16 + TypeScript
- PostgreSQL for catalog metadata
- Local persistent storage (`./uploads`)
- Python/PyMuPDF + Pillow inside the same application image for PDF processing
- Nginx serves generated page images directly

No MinIO. No PDF.js. No native browser PDF viewer for public catalogs.

## Public routes

- `/` landing page
- `/admin` catalog administration
- `/<slug>` opens page 1 of the image-based catalog
- `/<slug>/p/<page>` opens a specific catalog page/screen
- `/api/catalogs/<slug>/pdf` downloads the original PDF


## Screen navigation mode (v3.1)

The public catalog is **not a scrolling document**. Exactly one rendered PDF page is visible at a time and it is fitted inside the browser viewport without cropping.

- `/<slug>` = page 1
- `/<slug>/p/2` = page 2
- internal PDF hotspots update the URL and switch screens
- browser Back / Forward returns through catalog navigation
- linked destination images are preloaded while the current screen is visible
- there is no toolbar and no extra next/previous UI

This viewer change reuses the existing `manifest.json` and WebP files, so catalogs already generated by v3.0 do **not** need to be uploaded again. No new catalog or Nginx Compose mounts are required if generated images already work.

## 1. Fonts before building

Copy your Dana files to `public/fonts/` using these exact names:

- `Dana-Light.woff2`
- `Dana-Regular.woff2`
- `Dana-Medium.woff2`
- `Dana-DemiBold.woff2`
- `Dana-Bold.woff2`
- `Dana-ExtraBold.woff2`
- `Dana-Black.woff2`

The app has fallback fonts, so a build does not fail if these are absent, but Dana will only load when these filenames exist.

## 2. Build on your PC

```bash
docker build --no-cache -t badje-catalog:latest .
docker save badje-catalog:latest | gzip > badje-catalog-image.tar.gz
```

Copy to the server:

- `badje-catalog-image.tar.gz`
- `docker-compose.yml`
- `.env`

## 3. Server directory

Keep the files in a directory such as:

```text
/path/to/catalog.badje.ir/
├── docker-compose.yml
├── .env
└── uploads/
```

Create storage and make it writable by UID 1001 used inside the app container:

```bash
mkdir -p uploads/source uploads/generated uploads/.processing
chown -R 1001:1001 uploads
chmod -R u+rwX,go+rX uploads
```

If SELinux blocks bind-mount writes, use the appropriate shared container label for your host configuration (for example `:z` on the bind mounts).

## 4. PostgreSQL

Use your existing PostgreSQL container/server. Example:

```sql
CREATE USER badje_catalog WITH PASSWORD 'CHANGE_THIS';
CREATE DATABASE badje_catalog OWNER badje_catalog;
```

The application automatically creates the `catalogs` table if missing.

## 5. Environment

Copy `.env.example` to `.env` and set real values.

Example when PostgreSQL is exposed on the Docker host:

```env
DATABASE_URL=postgresql://badje_catalog:PASSWORD@host.docker.internal:5432/badje_catalog
ADMIN_USERNAME=admin
ADMIN_PASSWORD=VERY_STRONG_PASSWORD
SESSION_SECRET=LONG_RANDOM_SECRET_AT_LEAST_32_CHARACTERS
COOKIE_SECURE=true
MAX_UPLOAD_MB=200
CATALOG_RENDER_DPI=200
CATALOG_WEBP_QUALITY=96
CATALOG_WEBP_LOSSLESS=true
```

`CATALOG_WEBP_LOSSLESS=true` is the recommended test/quality mode. The page is still rasterized from the PDF, but WebP does not apply additional lossy compression.

## 6. Load and start on server

```bash
docker compose down
gunzip -c badje-catalog-image.tar.gz | docker load
docker compose up -d --force-recreate
```

Check:

```bash
docker compose ps
docker compose logs -f --tail=100
curl http://127.0.0.1:8000/health
```

Healthy response:

```json
{"status":"ok","database":"ok","storage":"ok","renderer":"ok"}
```

## 7. Nginx container mounts

The Nginx container must see the generated page images and original PDFs. Add these **absolute host paths** to the Nginx container's existing Compose file:

```yaml
volumes:
  - /ABSOLUTE/PATH/catalog.badje.ir/uploads/generated:/data/catalog-assets:ro
  - /ABSOLUTE/PATH/catalog.badje.ir/uploads/source:/data/catalog-source:ro
```

Do not use `./uploads` in the Nginx Compose unless that Compose file is in the same directory as the catalog Compose.

The included `nginx/catalog.badje.ir.conf` is ready for this mapping.

After adding new Nginx volume mounts, recreate the Nginx container (a config reload alone cannot add mounts):

```bash
docker compose up -d --force-recreate
```

Verify inside Nginx:

```bash
docker exec YOUR_NGINX_CONTAINER ls -lah /data/catalog-assets
docker exec YOUR_NGINX_CONTAINER nginx -t
```

## Upload processing

On create/replace:

1. Browser streams the PDF to Next.js.
2. The original is written to a temporary local file.
3. PyMuPDF renders each PDF page at the configured DPI.
4. Pillow stores the page as WebP.
5. PyMuPDF extracts link rectangles.
6. Internal destinations are stored as page numbers in the manifest.
7. The viewer turns them into `/<slug>/p/N` screen navigation.
8. External URIs become standard HTML links.
9. The completed output atomically replaces the previous generated version.

The admin request remains open during processing. Nginx proxy timeouts are set to 600 seconds in the included configuration.

## Storage structure

```text
uploads/
├── source/
│   └── <catalog-id>.pdf
├── generated/
│   └── <catalog-id>/
│       ├── manifest.json
│       └── pages/
│           ├── 0001.webp
│           ├── 0002.webp
│           └── ...
└── .processing/
```

## Existing old catalogs

Old MinIO/native-PDF records do not have generated web assets. In test mode, simply replace/re-upload the PDF for each existing catalog once. The same database row/slug is kept and a generated web version is created.

## Per-catalog quality and regeneration (v3.2)

Render quality is managed by the administrator for each catalog. The environment variables are only the defaults used when opening the create form.

In **کاتالوگ جدید** or **ویرایش کاتالوگ**, the admin can select:

- 150–400 DPI rendering (the UI provides 150/200/250/300/350/400 presets)
- Lossless WebP for maximum fidelity
- Lossy WebP for smaller output, with quality from 70–100

The selected settings are saved with the catalog record. The dashboard also records the generated page count and total generated image size.

Because the source PDF is stored separately, changing output quality does not require another upload. Open a catalog in Edit and use **بازسازی از PDF اصلی**, or change the quality and save. The app regenerates `uploads/generated/<catalog-id>/` from `uploads/source/<catalog-id>.pdf` and swaps the new output into place only after a successful render.
